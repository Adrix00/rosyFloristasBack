# ADR-005: PII Protection and Payment Tokenization

- **Status:** Accepted
- **Date:** 2026-08-16
- **Decision Makers:** Rosy Floristas Development Team

---

# Context

Rosy Floristas stores personal data of guests, registered customers and the recipients of a
delivery: names, emails, phone numbers, postal addresses and, for registered customers, payment
methods. A single database dump or a compromised backup should not be enough to expose this data
in plain text, but the application still needs to:

- send transactional email and call the recipient of a delivery;
- let the admin panel find a customer or an order by email or phone;
- charge a card without ever holding card data that falls under PCI-DSS.

A single strategy ("hash everything", "encrypt everything") does not satisfy all three needs at
once. Argon2 hashing, in particular, uses a random salt per row: two hashes of the same email never
match, which makes it unusable for `WHERE email = ?` or for a `UNIQUE` constraint.

---

# Decision

Each category of sensitive data gets the treatment that matches what the application actually does
with it, never a single default applied everywhere.

## Passwords

Argon2id, irreversible by design. Applies to `customers.password_hash` and
`admin_users.password_hash`. Never used for anything that needs to be searched or recovered.

## Data that must be recovered (sent, called, delivered, displayed)

AES-256-GCM, encryption key held outside PostgreSQL (environment variable / KMS), never in a
migration, a table or a config file checked into the repository.

Applies to: customer email and phone, first and last name, every field of
`customer_addresses`, the buyer snapshot in `orders` (`buyer_first_name_encrypted`,
`buyer_last_name_encrypted`, `buyer_email_encrypted`, `buyer_phone_encrypted`), every PII field of
`order_deliveries` (recipient name, phone, street, number, detail, latitude, longitude,
`card_message`), and `admin_users.totp_secret_encrypted`.

Latitude and longitude are encrypted together with the street: leaving the coordinates in plain
text while encrypting the address text would identify the exact doorstep and defeat the point of
encrypting the street at all.

## Data that must be searched by exact equality

HMAC-SHA256 with a pepper held outside PostgreSQL, stored as a deterministic `BYTEA` column
alongside the encrypted value. Because the same input always produces the same HMAC, it supports
`UNIQUE` constraints and `WHERE column = ?` lookups without ever storing the value in plain text.

Applies to: `customers.email_hash`, `customers.phone_hash`, `admin_users.email_hash`,
`orders.buyer_email_hash`, `orders.buyer_phone_hash`.

Consequence accepted on purpose: only exact-match lookup is possible. `first_name` and `last_name`
carry no HMAC, because a name is never looked up by exact equality — the admin panel searches
customers by email, phone or order number, never by partial name. Introducing a name search
mechanism is out of scope for this phase.

## Postal code

Stored in plain text (`customer_addresses.postal_code`, `order_deliveries.postal_code`). It is not
harmless — combined with other data it can contribute to re-identification — but its sensitivity is
materially lower than a full street address, and it is required in plain text for the delivery
pricing rule (distance-based tiers) and for by-zone sales metrics. The full address, and the
coordinates, remain encrypted. `distance_km` is likewise kept in plain text: it is a low-resolution
derived value needed to apply the shipping tariff, and required to make the shipping-fee logic
auditable in SQL.

## Payment cards — no PAN is ever stored

Cards are never tokenized in-house. The card number never reaches the backend: the payment gateway
(Stripe or equivalent) returns a token, and `customer_payment_methods` stores only
`payment_method_token`, `provider_customer_id`, `card_brand`, `last_four` and the expiry date. This
keeps the merchant in PCI-DSS SAQ A, the lightest self-assessment tier, instead of full-scope
PCI-DSS, which requires annual audits, network segmentation and key rotation infrastructure the
project has no reason to build.

## Session and verification tokens

`refresh_tokens.token_hash` and `verification_tokens.token_hash` use plain SHA-256, not Argon2.
These tokens are high-entropy random values generated by the application, not user-chosen
passwords: Argon2's deliberate slowness protects against guessing a low-entropy secret, which does
not apply here, and would only add latency to every authenticated request.

---

# Consequences

- Every service that reads or writes PII needs access to the encryption key and the HMAC pepper,
  both injected via environment/KMS, never persisted in the database.
- Customer search in the admin panel is limited to exact email, exact phone, or order number. No
  partial-name search in this phase.
- A leaked database dump exposes password hashes (useless without cracking Argon2id), HMACs (useless
  without the pepper) and ciphertext (useless without the key), but not the underlying values.
- Deleting a customer's PII (see ADR-007) is a `NULL`-out of these same columns; no separate secret
  store to purge.

---

# Alternatives considered

**Hash email and phone with Argon2, like passwords.** Rejected: Argon2's random salt makes two
hashes of the same value incomparable, which breaks both the `UNIQUE` constraint on email and the
"find this guest's past orders by email" flow required for account promotion.

**Store cards ourselves, encrypted.** Rejected: encrypting the PAN does not remove it from PCI-DSS
scope. The card number would still have touched the backend, still require a documented key
lifecycle, and would put the project in full-scope PCI-DSS for no functional gain over tokenization.

**Encrypt everything, including postal code and distance.** Considered and rejected for these two
fields specifically: both are required in plain text by SQL-level business rules (shipping tariff,
zone metrics), and their sensitivity is judged low enough, in this application's context, to accept
plain text. Every other field with comparable exposure risk (street, coordinates, names) stays
encrypted.
